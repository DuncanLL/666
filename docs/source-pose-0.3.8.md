使用实际已安装Project Viewpoint ADS 1.9.1二进制（SHA256 `56c802cd04ffc6b9388aa2c550f2dbde555997949cfedfd0bedf872fa44bb84e`）和真实游戏AnimationPlayer/骨架，私有检查调用其原有方法：

1. 正常动作矩阵全部有限、可逆。
2. `raiseHideArms`将14块共享显示矩阵缩放为零。
3. 在显示姿态被继续读取的受控顺序中，`steadyArms`对零尺度锚点求逆/取得旋转，并把12块手臂矩阵写成NaN。

不调用任何胸部物理解算即可复现，因此胸部物理不是这条链的必要条件。为什么反馈现场只在有胸部物理的角色上观察到，仍未证明；耗时、缓存复用或过渡时序只能列为假设，不写成结论。原日志另有旧CameraView接口/torchCount错误，本轮不处理这些扩展的独立API兼容问题。

## 公共修复

生产代码无ADS、角色、武器或动作名称判断，不改外部模组文件，不分发其闭源实现。只在使用R116的角色上接三处现有游戏阶段：

- 完成游戏自身骨骼矩阵计算后，记录本次真实动作的全局/局部姿态作为有界参考；每角色一次分配，随后复用。
- 读取骨骼时，正常有限、可逆的矩阵完全原样返回，保留合法显示/瞄准修正。若共享显示矩阵已非有限或奇异，先调用游戏自身FK从当前动画局部数据重建；若显示阶段连局部数据也损坏，只能使用本次有效动画评价的参考恢复相应局部/全局数据。不是补零、固定角度、休止姿态或上一帧冻结。
- 游戏蒙皮读取底层数组、绕过骨骼getter，所以进入蒙皮前也检查对应骨骼；恢复后调用游戏自己的缓存失效方法，避免继续使用已坏的蒙皮缓存。

真实动作自身的零缩放保持零缩放；真实动画评价自身已无效时不使用旧参考蒙混通过，原严格异常检查保留。没有吞掉异常、反复重置物理或按故障停用胸部效果。正常动作不改，原有物理、70%手型、60Hz、材质和语音不变。

## 验证和开销边界

- `tools/check_source_pose.py`通过实际ZombieBuddy Advice测试上述模块原方法。修前12块NaN；修后不产生NaN，完整捕获后无奇异骨骼。60轮显示调用、不同间隔、共享姿态复用通过。
- 16个原版动作加True Actions YMCA，51个实际采样点，新旧有效姿态最大差值0。覆盖站走跑、蹲、持枪及抬放枪、坐地、翻越、挥击和舞蹈；这不是完整游戏动作图/输入控制实测。
- 反向检查：非R116角色不被修复；正常反射/小尺度有效矩阵逐字段保持；真正动画零缩放不变；动画源本身无效仍拒绝；关闭R116释放守护所有权；蒙皮缓存能正确重建。
- 3个人物各120帧动作/舞蹈输入，新旧采样位置和法线最大差值0；所有非class JAR载荷，包括原生库和胸部绑定逐字节相同。候选工坊及11模型原生组件通过，结束对象计数归零。
- getter微测量末轮约300000次2.65ms，旧调用约0.40ms；3000次动画评价在有/无所有权下约2.94/2.34ms。这只是方法组件微测量，不宣称实际FPS成本。正常读不分配参考数组，修复仅在坏数据出现时执行重建；没有新线程、解算器、绘制Pass或物理频率。
