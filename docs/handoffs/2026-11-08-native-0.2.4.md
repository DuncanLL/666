# Native 0.2.4：共用原游显示衔接与连续强度

## 当前用户边界

以整备室为主要人物观感参考；人物继续接受 VP 现场光照与反射；所有角色共用材质/显示接入。VP 原版环境、天空、雾、曝光及场景后处理保持，不写角色美白分支，不照搬整备室的灯位、SH或固定房间反射。

用户认为完整转换的图目前偏亮，可作为峰值；要求进游戏连续调节。新增 `characterDisplayStrength`：0–1、步长0.01、默认0.5、跨质量预设保留。0是旧人物显示路径（少前2材质仍启用），1是完整原游显示转换，其他值在这两条人物颜色输出间连续过渡。与既有 `characterSoftFill` 底灯独立；对照图底灯为0，安装时保留用户已有底灯设置。

## 共用实现

- `AimohNativeDisplayTransfer` 只接收原游共用颜色资料、VP实时参数和输出附件信息；没有角色名、角色ID或衣装特判。
- 原资源来自实际 `_TONEMAP_UNREAL_FILMIC` 程序及三个实际帧均一致的256KiB表，原程序重建验证详见还原审计。没有新增手调肤色、暖色去色或造景灯组。
- `AimohGf2DisplayTables` 组合原游显示与实际 Native Filmic 反向响应；VP数值从公开的 CPU live 数组读，曝光单独处理。颜色表缓存，仅相关显示参数改变时更新；强度与曝光变化不重新造表。
- 复用已有运动/法线交接计算，没有额外场景渲染、绘制或dispatch。两种接收编码各缓存一份表，GPU共0.5MiB；这比隔离证明单表0.25MiB多一份，但每帧只绑定其中一份。
- 保守覆盖：只处理有GF2不透明/深度归属标记的像素。没有明确归属的背景、透明边缘不强行转换；透明/遮挡完整视觉仍未验收。原法线、速度、深度和alpha不作颜色处理。
- 非Filmic或不可反向求解的设置保留Native响应；共享资料缺失/校验失败时也保留原人物显示，不因可选显示表失败中断人物绘制。尚不宣称所有显示曲线和极端颜色设置均可精确匹配。

## 资料与分发

共用二进制不进Git，`resources/manifest.json` 的 `render_support.original_display_profile` 登记文件、大小与指纹；实际资产根放 `.local/paths.json` 的 `render_support_asset_root`。可用 `tools/build_render_support.py --read-assets-from <包含该资料的配套JAR>` 从匹配版本回读，再正常构建。

构建将它内嵌为JAR资源 `aimoh/gf2/bridge/gf2-original-display.rgba16f`。人物catalog仍是原来的八类字段，新角色照常追加自己的真实资料，不复制显示表或增写专用算法。内部MOD ID和工坊项目保留。原有格式12/DXT5兼容更新在源码中保留，未回盖其他对话的人物/核心更新。

## 验证边界

- 共同数学实现与参考结果最大差约一个半精度步；黑色、不合法输入、Native参数变化已做检查。
- 科莱达、夏安、阿斯缇亚夜间室内受控绘制无GL错误，空场景与旧输出逐字节一致。源资料错误能保留旧响应；新增两张LUT实际释放检查通过。
- 显示参数变化会重建表；单纯曝光或还原强度变化复用原表。0/0.5/1及实时切换另有受控记录。
- 720×900、AMD9070XT、单人物稳定样本的复用计算GPU耗时，禁用约0.01316ms，启用约0.01798ms，差约0.00482ms；这是该计算步骤，不是整体MOD FPS或跨硬件保证。两表首次CPU准备实测约30ms，非逐帧路径。
- 普通Java MOD分派、自动安装/发现、共享资产校验和工坊目录检查通过。真实游戏显示格式、夜景观感、透明边缘及用户调参仍须实测；NVIDIA/低端和真实订阅冷启动未确认。
