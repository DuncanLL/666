# 人物框架联机

适用目标为 PZ 42.22。房主在服务器设置里启用 ZombieBuddy、一个版本的人物框架，以及要开放的人物模块。客户端使用同一份人物包。框架与人物包保持原有工坊条目及 MOD ID。

## 玩家流程

1. 进服后，客户端读取服务器给当前账号的钱包和已穿戴外观。服务器进度按 PZ 用户名写入当前世界的 ModData，角色死亡后新建生还者仍可读取。单机使用原来的钱包。
2. 在人物框架中点头像只预览。服务器按已启用的人物包、余额和保底核算抽卡、现金兑换及衣装购买。抽到后客户端播放结果，玩家再点「启用」。
3. 服务器先确认穿戴权限，客户端加载模型。模型成功后，服务器再次检查归属和包状态，再向其他人发布外观。重连时读取服务器已保存的外观，已下架的模型在服内停用。
4. 远端客户端读取本地同版模型和资源。网络只传模型 ID、模型配置指纹、配件选择与材质显隐。远端复用 PZ 动作和持物，次级物理关闭。特效与光影按每位观看者的渲染后端绘制。

## 运行开销

单机加载联机模块时直接返回，不注册联机事件、轮询或网络请求。窗口初始化时记录会话类型，后续单机刷新不查询联机状态。多人会话每 250 毫秒处理客户端维护任务，重复的外观状态不再次发送。角色的每帧动作、物理和光影仍走现有绘制流程。

## 代码入口

- `AimohPMXNetwork.lua` 维护服务端钱包、校验请求、保存穿戴并发送快照。
- `GFL2MultiplayerClient.lua` 管理连接握手、请求重发和远端外观生命周期。
- `AimohPMXRoomEconomy.lua` 是单机与服务端共用的价格和抽卡规则。联机客户端只读内存中的服务器钱包快照。
- `GFL2MultiplayerCatalog.lua` 由框架和角色包资料生成。修改模型、价格或卡池后运行 `py -3 tools/generate_multiplayer_catalog.py`，用 `--check` 验证生成结果。
- `Main.java` 解析配件和显隐，使用现有角色会话完成本机和远端绘制。

每个账号一次处理一笔经济请求，客户端超时后用相同序号重发。服务器保留最近一次的请求及结果。多人并发窗口、不同进程的真实掉线重连，以及服务器异常退出时 PZ 背包和 ModData 各自的落盘行为，需要实际联机验证。发布前先测原版视角双端，再测正式版 Viewpoint 和 RC4，最后测同屏性能。
